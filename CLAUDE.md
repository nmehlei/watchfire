# CLAUDE.md — Watchfire

This file is for AI coding agents. Read it start to finish before taking any action.

## What Watchfire is

Watchfire is an autonomous, read-only SRE agent that watches infrastructure across multiple tenants on behalf of
an operator. It sends nightly digests and real-time pages through Telegram, and runs
on a budget of a few euros a month (see `specs/00-overview.md`).

**Report-only, always.** Never write, never mutate, never deploy. Several independent
layers enforce this — reader-scoped credentials, a command allowlist, and a
forced-command shell on SSH targets. Your code must respect this invariant without
exception.

## Repository shape

An npm-workspaces monorepo:

- `apps/agent/` — the agent (`@watchfire/agent`): adapters, runner, memory, API
- `apps/dashboard/` — the Next.js dashboard (`@watchfire/dashboard`)
- `specs/` — the specification; `docs/` — usage, operations, deployment, integrations
- `infra/ssh/` — the constrained shell installed on monitored hosts
- `brand/` — logo sources, generated by `brand/build.mjs`

Install once at the root with `npm ci`. Scripts run per workspace:
`npm test -w @watchfire/agent`, `npm run build -w @watchfire/dashboard`.

## Source of truth

The `specs/` directory is authoritative. Read it before writing code. In intended
reading order:

- `specs/00-overview.md` — goals, non-goals, principles, budget
- `specs/01-architecture.md` — components, run loop, deployment, secrets
- `specs/02-tenants.md` — tenant definitions, credential scopes, resource graph
- `specs/03-systems.md` — adapter contracts per system type (**partial**)
- `specs/04-nightly.md` — prompt structure, sweep ordering, turn budget, finding extraction
- `specs/05-watch.md` — webhook intake, triage budget, verdict protocol, rate limiting
- `specs/06-memory.md` — SQLite schema, fingerprinting, lifecycle, retention, query patterns
- `specs/07-reporting.md` — finding rendering, digest and page structure, Telegram send path
- `specs/08-safety.md` — safety hook, watchfire-shell forced-command, audit
- `specs/10-telegram-control.md` — Telegram bot command surface (mute / unmute / mutes / help)
- `specs/11-mcp.md` — external read surfaces: MCP for Claude sessions, REST for the dashboard
- `specs/12-dashboard.md` — Next.js dashboard (PWA, Entra ID, App Service)

`specs/README.md` records which specs are implemented and which run ahead of the
code. `docs/operations.md` is the operator guide (it was once spec 09).

Changes to behaviour start with a spec edit, then a code change. Don't skip the spec
step.

## How to work in this repo

**Read before you write.** When asked to implement anything, first re-read the
relevant spec sections. If the spec is silent or ambiguous, stop and ask. Do not
invent behaviour.

**Spec changes are a pull request like any other.** If an implementation need
uncovers a spec gap, propose the spec change first, get it approved, then implement.
Don't edit specs and code in the same commit — split them.

**Living documents.** Specs evolve. `git log specs/` is the design history.

**Self-report after every spec draft or significant change.** At the end of each
response where you drafted or meaningfully edited a spec, include a short
"Notes for the operator" block:

1. **Inferred** — decisions you made that weren't explicit in the specs. Flag even small ones.
2. **Unsure** — things you're genuinely uncertain about and want input on.
3. **Tensions** — anything that sits uneasily with earlier specs, even if you think it's fine.
4. **Skipped** — questions you noticed but deliberately didn't address, and why.

Keep it brief. If a category is empty, omit it. Never fabricate entries to fill the
block — its value depends on being signal, not noise.

**Conventions:**
- TypeScript, ESM, Node 24+
- Strict TS, no `any` without an adjacent comment explaining why
- Business logic in pure functions; side effects at the edges
- One adapter per directory under `apps/agent/src/adapters/<system>/`
- CLI wrappers in `apps/agent/bin/` are thin — they call into `apps/agent/src/`
- Tests alongside code: `foo.ts` + `foo.test.ts`, Vitest
- No runtime dependencies beyond those in `specs/01-architecture.md`'s stack
- Secrets never logged, never stringified into errors, never in tests

**Safety bar for every change:**
1. Does any new command need handling in the safety hook? (`apps/agent/src/agent/safety.ts`)
2. Does any new adapter's credential have read-only rights, and is its setup documented
   in `docs/integrations/`?
3. Does any new secret stay out of the repository and the tenant registry, which holds
   only environment-variable *names*?

## Project status

What is built:

- Tenant registry and resource graph, memory (findings, runs, observations, mutes,
  retention), the safety hook, and the agent runner.
- Adapters: OpenObserve (`obs-search` and `obs-streams` live; `obs-metrics` and
  `obs-alerts` stubbed), `check-ssl`, `check-http`, `check-ado`.
- Nightly: schedule, startup catch-up, agent run, digest, transcript archival.
- Watch: OpenObserve and Telegram webhooks, a bounded queue, a triage agent, page
  rendering, and mutes via Telegram commands.
- API (spec 11): MCP at `/mcp` and a REST surface under `/api/` for findings, runs,
  mutes, cost and adapter health — on the same Fastify server, gated by `WATCHFIRE_API_TOKEN`.
- The dashboard, in `apps/dashboard/`.

What is still ahead:

- The Azure Resource Manager, Hetzner Cloud and Kubernetes adapters, and SSH-based
  checks — specified in `specs/03-systems.md`, not built.
- A built-in heartbeat, so that Watchfire stopping is itself noticed.
- Operational hardening as real findings reveal weak spots.

**Do not leap ahead.** When adding adapters, build vertically — one adapter end to end
— not horizontally. The current shape is robust because it grew that way.

## Collaboration

- Be direct and concise. Push back when you disagree.
- Keep messages short when work is going well; explain at length only when there is a
  real trade-off to discuss.
- Keep pull requests small enough to review in one sitting.

## Guardrails you must never cross

- Do not commit plaintext secrets. There is no pre-commit hook — nothing catches it for you.
- Do not add mutating capabilities "just in case" — they violate the report-only invariant.
- Do not change the default model (`claude-haiku-4-5`) without approval — it sets the budget.
- Do not add features not grounded in a spec section.
- Do not loosen a safety-hook or `watchfire-shell` pattern without a reviewed spec change.

## When stuck

Ask. One good question beats ten assumptions.
